# Права доступа по юзерам — дизайн

Дата: 2026-07-27

## Проблема

В проекте нет модели авторизации. Все коллекции защищены одной функцией:

```ts
export const authenticated = ({ req: { user } }) => Boolean(user)
```

Правило буквально одно: «залогинен → можно всё». Юзер, заведённый под блог,
сегодня может править Page Contents, удалять Media, читать Form Submissions,
переписать глобалы Header/Footer и создавать или удалять других юзеров —
включая аккаунт владельца.

Ролей в Payload нет из коробки, поэтому модель прав надо строить. В коллекции
`Users` сейчас только `email` и `name`.

## Цели

- Права выдаются **по юзеру, по коллекции, по операции**
  (`read` / `create` / `update` / `delete`), редактируются галочками в админке —
  без деплоя.
- Публичный фронтенд продолжает работать ровно как сейчас.
- Не-админ не может повысить сам себя.
- Во время выката никто не должен потерять доступ в `/admin`.

## Вне задачи

- Система ролей/пресетов. Права ставятся на юзера. На двух-трёх редакторах это
  проще и прозрачнее; пресеты можно накинуть поверх позже, не трогая слой
  доступа.
- Отдельное право `publish`. `update` включает право публиковать (решение
  принято при обсуждении).
- Права на уровне полей. Гранулярность заканчивается на коллекции.

## Исследование готовых решений

Проверено перед тем, как писать своё.

**Официального RBAC у Payload нет и в 3.86.** Документация и блог
[Build Your Own RBAC](https://payloadcms.com/posts/blog/build-your-own-rbac)
предлагают писать access-функции самостоятельно; их пример — поле роли на юзере,
без скрытия коллекций из сайдбара, без защиты поля ролей и без сценария
лок-аута.

Состояние сообщества на 2026-07-27 (данные из npm registry):

| Пакет | Версия | Peer payload | Загрузок/мес | Вывод |
| --- | --- | --- | --- | --- |
| `payload-gatekeeper` | 1.1.0, 2025-08-18 | `>=3.0.0 <4.0.0` | 651 | живой |
| `roles-privileges-payload-plugin` | 1.2.3, 2025-12-21 | `^3.69.0` | 76 | живой |
| `payload-rbac` | 1.0.3, 2023-04-18 | `^1.6.22` | — | мёртв, Payload 1 |
| `@nouance/payload-simple-rbac` | 0.2.0, 2023-04-17 | `^1.6.22` | — | мёртв, Payload 1, BETA |

Оба живых плагина функционально закрывают задачу: `roles-privileges`
автогенерирует CRUD-привилегии на все коллекции и глобалы с UI из чекбоксов,
`gatekeeper` использует строковые права с вайлдкардами (`posts.read`, `posts.*`)
и автоматически выдаёт super_admin первому юзеру.

Почему всё-таки своё:

1. **Оба role-based.** Появляется коллекция Roles — сущность, которой мы
   осознанно не хотим.
2. **Публичное чтение — не булево.** Аноним должен видеть Posts/News/Case
   Studies только опубликованные, то есть access обязан вернуть Where-констрейнт
   `{ _status: { equals: 'published' } }`, а не `true`/`false`. Оба плагина
   оборачивают доступ проверкой привилегии; сохраняется ли под обёрткой
   Where-констрейнт — в документации не описано. Непроверенное поведение здесь
   означает либо погасший сайт, либо черновики в проде.
3. **Цена риска.** Это слой авторизации: его баг — дыра, а не упавшая сборка.
   При таком объёме внедрения отлаживать пришлось бы чужую обёртку.

Свой слой на 11 коллекций — порядка 150 строк без зависимостей. При редакции на
20 человек с иерархией ролей вывод был бы обратным — брать `payload-gatekeeper`.

Из плагинов заимствуются две идеи: автовыдача полного админа первому юзеру и
явные права на глобалы.

## Находка, определившая дизайн

Payload заново читает документ юзера из базы на **каждом** аутентифицированном
запросе (`payload.findByID` в
`payload/dist/auth/strategies/jwt.js:69`), а не доверяет claim-ам из JWT.
Отсюда:

- `req.user` всегда несёт актуальные права;
- изменение прав действует со следующего запроса — перелогин не нужен,
  `saveToJWT` для проверок доступа не нужен.

## Дизайн

### 1. Единственный источник правды

`src/access/permissions.ts` держит список управляемых коллекций и операций.
Больше нигде в коде коллекции не перечисляются. Добавление коллекции в модель —
правка одной строки, которая одновременно добавляет её в форму юзера, в проверки
доступа и в логику скрытия сайдбара.

```ts
export const MANAGED_COLLECTIONS = {
  posts: 'Posts',
  news: 'News',
  'case-studies': 'Case Studies',
  'page-content': 'Page Contents',
  media: 'Media',
  categories: 'Categories',
  tags: 'Tags',
  authors: 'Authors',
  forms: 'Forms',
  'form-submissions': 'Form Submissions',
  redirects: 'Redirects',
} as const

export const OPERATIONS = ['read', 'create', 'update', 'delete'] as const

export type ManagedCollection = keyof typeof MANAGED_COLLECTIONS
export type Operation = (typeof OPERATIONS)[number]
```

Ключи — реальные слаги коллекций, поэтому опечатка становится ошибкой типов в
месте вызова, а не молчаливой дырой в правах.

### 2. Как права лежат на юзере

Два новых поля в `Users`:

| Поле | Тип | Смысл |
| --- | --- | --- |
| `fullAdmin` | `checkbox` | Суперюзер. Игнорирует матрицу, управляет другими юзерами и их правами. |
| `permissions` | `group` | По одному `select hasMany` на каждую управляемую коллекцию, опции = `OPERATIONS`. |

Группа `permissions` скрывается в UI, когда стоит `fullAdmin`
(`admin.condition`), — она бы всё равно не читалась.

Поля группы генерируются из `MANAGED_COLLECTIONS`, а не пишутся руками:

```ts
const toPermissionField = ([slug, label]: [string, string]): Field => ({
  name: slug,
  type: 'select',
  hasMany: true,
  label,
  options: [...OPERATIONS],
})

const buildPermissionFields = (): Field[] =>
  Object.entries(MANAGED_COLLECTIONS).map(toPermissionField)
```

Что видит админ в форме юзера:

```
Full admin  [ ]

Permissions
  Posts             [read] [create] [update] [delete]
  News              [read] [create] [update] [delete]
  Media             [read] [create] [update] [delete]
  ...
```

Три слага содержат дефис (`case-studies`, `page-content`, `form-submissions`).
Payload отклоняет только имена полей с точкой
(`payload/dist/fields/config/sanitize.js:67`), так что это валидные имена полей и
читаются через скобочный доступ — ключ матрицы остаётся идентичен слагу
коллекции.

### 3. Фабрика доступа

```ts
const isFullAdmin = (user?: User | null) => Boolean(user && user.fullAdmin)

const can =
  (collection: ManagedCollection, operation: Operation): Access =>
  ({ req: { user } }) => {
    if (!user) return false
    if (isFullAdmin(user)) return true

    const granted = user.permissions?.[collection]
    if (!granted) return false

    return granted.includes(operation)
  }
```

Коллекция подключается одной строкой:

```ts
access: collectionAccess('posts')
```

где `collectionAccess` возвращает `{ create, update, delete, read }`, собранные
из `can(...)` плюс правило чтения ниже.

### 4. Семантика `read` — место, которое нельзя сломать

Фронтенд читает Media, Categories, Tags, Authors и Page Contents анонимно, а
Posts/News/Case Studies — с фильтром по опубликованным. Если отдать `read` под
управление матрицы целиком, публичный сайт погаснет.

Поэтому `read` в матрице означает **«видит коллекцию в админке и видит
черновики»**, а публичное правило сохраняется под ним:

| Коллекция | Аноним / нет права `read` | С правом `read` |
| --- | --- | --- |
| `posts`, `news`, `case-studies` | только опубликованное (`_status: published`) | всё, включая черновики |
| `media`, `categories`, `tags`, `authors`, `page-content` | полное чтение (как сейчас, `anyone`) | полное чтение |
| `forms` | полное чтение (как сейчас — сайт рендерит формы) | полное чтение |
| `form-submissions` | запрещено | полное чтение |

`form-submissions.create` остаётся `() => true`, иначе перестанет работать
отправка формы с сайта. Матрица управляет там только `read` / `update` /
`delete`.

Хелпер, заменяющий `authenticatedOrPublished`:

```ts
const publishedOrPermitted =
  (collection: ManagedCollection): Access =>
  (args) => {
    if (can(collection, 'read')(args)) return true
    return { _status: { equals: 'published' } }
  }
```

### 5. Поверхность админки

- `admin.hidden` на каждой коллекции считается из той же матрицы: у кого нет ни
  одного права на коллекцию — тот вообще не видит её в сайдбаре, вместо «вижу,
  кликаю, получаю 403».
- `Users.access.admin` пускает в `/admin` полных админов и тех, у кого есть хотя
  бы одно право; остальных разворачивает на входе.
- Поля `permissions` и `fullAdmin` остаются **читаемыми** своим владельцем.
  Скрытие сайдбара считается на клиенте из документа `/me`, поэтому запрет на
  чтение этих полей сломал бы скрытие. Ограничивается только `update`.

### 6. Защита от самоповышения

| Поверхность | Правило |
| --- | --- |
| поле `fullAdmin` | `access.update` → только полные админы |
| поле `permissions` | `access.update` → только полные админы |
| `Users.read` | полный админ видит всех, остальные — только себя (`{ id: { equals: user.id } }`) |
| `Users.create` / `Users.delete` | только полные админы |
| `Users.update` | полный админ, либо юзер правит свой документ (имя/пароль — два привилегированных поля заблокированы отдельно) |

Без блокировки на уровне полей post manager открыл бы свою карточку и поставил
себе `Full admin`.

### 7. Глобалы

У `Header` и `Footer` объявлен только `read: () => true`, `update` не задан —
значит работает дефолт Payload и навигацию сайта может переписать любой
залогиненный.

Глобалы выдаются **по отдельности, как и коллекции**: список `MANAGED_GLOBALS`,
доступ через `globalAccess('<slug>')`, скрытие через `hiddenForGlobal('<slug>')`.
Изначально дизайн держал их вне матрицы (только полный админ), но это отнимало
осмысленный сценарий — доверить человеку правку футера, не отдавая ему весь сайт.
Технических препятствий нет: у глобалов есть и `update`, и `admin.hidden`.

Форма прав у глобалов другая, чем у коллекций, и намеренно: не сетка операций, а
один плоский список чекбоксов `Globals`. Выдавать там нечего, кроме права
редактировать — `read` глобала это то, что делает публичный сайт на каждой
странице, а create и delete у глобалов не существует. Сетка с одной колонкой
была бы ложной симметрией.

Скрытие здесь не косметика, а часть того же правила, что и для коллекций:
глобал, оставленный в навигации при запрещённом `update`, выглядит как рабочий
раздел — редактор открывает его, правит и узнаёт о запрете только по ошибке при
сохранении.

Отдельно: `canEnterAdmin` пускает в панель и того, у кого выдан только глобал —
иначе «редактор футера» упирался бы в `/admin/unauthorized`.

### 8. Коллекции плагинов

Дефолты проверены в `node_modules`:

| Коллекция | Дефолт плагина | Проблема |
| --- | --- | --- |
| `forms` | `read: () => true`, остальное не задано | любой залогиненный создаёт/правит/удаляет формы |
| `form-submissions` | `create: () => true`, `read: authenticated`, `update: () => false`, `delete` не задан | любой залогиненный удаляет заявки |
| `redirects` | `read: () => true`, остальное не задано | любой залогиненный правит редиректы |

Все три принимают переопределение доступа — `overrides.access` у редиректов,
`formOverrides.access` и `formSubmissionOverrides.access` у form builder, —
поэтому подключаются к матрице прямо из `src/plugins/index.ts`, без форка
плагинов.

`payload-folders` (появляется из-за `folders: true` у `Media`) остаётся на
дефолте и прячется из сайдбара: контента там нет, только группировка, а доступ к
папкам без доступа к медиа бессмыслен.

### 9. Bootstrap — риск лок-аута

У существующих документов юзеров в MongoDB нет ни `fullAdmin`, ни
`permissions`. Выкатить правила доступа, не проставив их, — значит получить
**ноль админов и никакой возможности назначить админа**: панель закрывается для
всех, чинится только правкой базы руками.

Решение: `scripts/grant-full-admin.ts`, запускается через
`pnpm payload run scripts/grant-full-admin.ts <email>`. Скрипт работает через
Local API, который по умолчанию обходит проверки доступа, поэтому сработает даже
при уже закрытой панели. Порядок выката — часть плана, а не примечание:

1. **до деплоя** прогнать скрипт с локальной машины против продовой базы
   (`DATABASE_URL='<прод>' pnpm payload run scripts/grant-full-admin.ts <email>`);
   локальный `.env` смотрит на другую базу, так что переменную надо передать явно;
2. убедиться, что у аккаунта владельца в базе стоит `fullAdmin: true`;
3. деплоить.

Порядок именно такой: `fullAdmin` — обычное поле документа, его можно проставить
до того, как код с правилами доступа окажется на проде, и тогда окна лок-аута не
возникает вовсе. Обратный порядок оставляет продакшн без админов на всё время
между деплоем и запуском скрипта.

Дополнительно: хук `beforeChange` на `Users` выдаёт `fullAdmin` первому
создаваемому юзеру (идея из `payload-gatekeeper`), чтобы новое окружение с
пустой базой не требовало ручного скрипта.

## Проверка

Руками, на локальном инстансе с двумя аккаунтами (полный админ и post manager с
правами `posts: всё`, `media: read+create`, `categories/tags: read+create`,
`authors: read`):

1. Post manager видит в сайдбаре только Posts, Media, Categories, Tags, Authors.
2. Post manager создаёт пост, грузит в него картинку, публикует.
3. Post manager открывает свою карточку — `Full admin` и `Permissions` видны, но
   не редактируются; отправка изменённого payload через REST возвращает 403, а не
   молча применяется.
4. Post manager не может открыть `/admin/collections/users` дальше своего
   документа.
5. Анонимный `GET /api/posts` по-прежнему отдаёт опубликованные посты, черновиков
   в выдаче нет.
6. Анонимный `POST /api/form-submissions` по-прежнему проходит.
7. У полного админа доступ ко всему, включая глобалы.
8. `pnpm lint` и `pnpm build` проходят.

## Оставшийся риск

Права по юзерам не масштабируются на большую редакцию — нельзя поменять правило
десяти людям сразу. На текущих двух аккаунтах это верный размен; если команда
вырастет, поверх той же матрицы добавляются пресеты, не трогая конфиги
коллекций.
